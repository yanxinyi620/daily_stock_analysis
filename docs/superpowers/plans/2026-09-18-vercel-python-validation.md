# Vercel Python Functions 单用户可行性验证计划

> **已弃用（2026-09-18）。** 用户已改用 [本地 Runner 方案](../../deployment/vercel-supabase-plan.md)，停止 Vercel Python 分析、流式问股与 Serverless 可行性试验路线。以下仅为历史计划，不是待执行任务，也不是验证成功记录。

> 执行时使用 superpowers:executing-plans，逐关验收。本文是用户指定路线的验证计划，不是已经部署成功的结论；不自动 commit、push 或修改线上别名。

**Goal:** 验证无需本地电脑、无需常驻服务器的单用户版本，真实运行单股分析、大盘复盘和受限网络 API 流式问股，并在函数实例更换后保留业务数据。

**Architecture:** 保留 React/Vite、Supabase Auth/RLS/Storage 和现有 Python 引擎；新增请求生命周期内执行的轻量 Python ASGI 入口，持久状态写 Supabase。GitHub Actions 不参与网页执行链路。

**Tech Stack:** React/Vite、FastAPI/ASGI、现有分析模块及网络模型 SDK、Vercel Python Functions、Supabase Postgres/Auth/Storage。

## 1. 与旧计划的关系

本计划取代“网页长期只读报告、Python 必须在本地执行”的后续产品边界，但不抹去此前已完成的部署、认证、报告发布和恢复验收。用户原稿 `docs/daily_stock_analysis_codex_plan.md` 保持原样。此前关于“不在 Vercel 执行 Python”的约束，在本轮验证范围内由用户的新指令替代。

本轮只重新规划，不部署函数、不调用模型、不迁移数据库。只有真实验证通过的能力才进入正式站点；不预先承诺三条链路都能适配免费资源。

| 能力 | 第一轮范围 | 后续条件 |
| --- | --- | --- |
| 登录、自选股、报告、下载、改密 | 继续保留 | 不回退既有用户隔离 |
| 单股分析 | 一次请求一只股票、指定账号、前台同步执行 | 真实运行和持久化通过后开放 |
| 大盘复盘 | 单次选择一个市场范围 | 多市场聚合后续分步处理 |
| 问股 | 网络 API 后端、一轮输入、有限上下文/工具调用、SSE | 不调用本地桌面端或本地模型进程 |
| 综合分析 | 第一轮不执行 | 单股与复盘均通过后，逐步调用并保存中间结果 |
| 回测 | 第一轮不开放 | 单独验证少量股票、有限日期窗口的成本与内存 |
| 重型选股、全市场批处理、离线后台任务 | 不在首版范围 | 不用伪后台或扩大超时来掩盖限制 |
| 数据源、模型与 Token | Vercel 服务端环境变量管理 | 暂不提供网页编辑密钥 |
| 原 CLI、Docker、本地 Web、桌面端 | 保留已有代码与默认行为 | 不为试验删除功能 |

单用户表示只有指定账号具备新计算能力，不删除已有 B 测试用户或历史报告。B 继续作为越权测试账号，不自动获得计算权限。允许的 owner 从服务端配置读取，不能由请求指定。

## 2. 已核实的实现基础与阻碍

- `src/services/analysis_service.py` 的 `AnalysisService.analyze_stock()` 是现有同步入口，内部调用 `StockAnalysisPipeline.process_single_stock()`；优先复用，不经本地异步任务队列绕行。
- `src/core/market_review.py` 的 `run_market_review()` 支持结构化返回；当前 API 包装包含后台执行和本地文件锁，不能直接照搬。
- `api/v1/endpoints/agent.py` 已有 SSE、executor factory 和请求内线程桥接；`src/services/agent_chat_session_service.py` 依赖 `DatabaseManager`。必须保留请求内流式生命周期，不使用研究模式的后台执行器。
- `api/app.py` 的 lifespan 会构造 RuntimeSchedulerService，并启动股票索引后台刷新；云端入口不得直接复用这些副作用。
- `src/config.py` 的 `get_db_url()` 当前构造 SQLite URL；`src/storage.py` 启动执行全量 create_all、自动补 schema，且日志输出数据库 URL。接入带密码的远端 DSN 前必须解决脱敏与启动迁移问题。
- `requirements.txt` 同时包括行情、模型、Bot、桌面/本机集成等依赖，存在平台 wheel 与二进制工具要求。不能通过测试夹具或删除真实分析依赖，制造一个只会返回成功的空函数。
- `apps/dsa-web/vercel.json` 当前 `/api` 固定 404；目前上传产物仅前端。验证包必须覆盖仓库 Python 代码和受控依赖，不能只在现有前端目录添加文件就宣称后端已部署。
- 现有 `analysis_tasks` 是发布任务，状态含 publishing，不是执行队列。新执行状态单独建表或明确关联，不改旧状态枚举的含义。

## 3. 部署方案选择

采用独立、可重复生成的试验部署包：复用前端源码/构建产物，打包必要 Python 源文件和精简但真实的依赖清单；在隔离的 Vercel Preview 或单独 Free 测试项目验证，暂不移动正式域名。不创建新的付费资源，不清空现有 restore 项目。

该方案比直接将完整 `server.py` 部署到线上更容易控制初始化副作用；比拆出独立后端域名少一层跨域配置。验证通过后再决定同项目根目录构建配置，保留一套可复现打包脚本，禁止手工复制形成第二套引擎源码。

拟新增部署资产位于 `scripts/`、`docker/` 同级的部署职责范围内，以 `scripts/build_vercel_python_bundle.py` 及 `requirements-vercel.txt` 管理；轻量入口使用 `api/serverless.py`。入口只注册经过验收的端点与身份依赖，不自动注册原系统全部管理 API。

应用依然在请求中完成工作。可在该请求内使用受控线程桥接同步库，但不得在响应结束后依赖线程、进程内队列、文件锁或 BackgroundTasks 继续完成业务。不以 202 + 无消费者的 pending 记录伪装后台任务。

## 4. 平台限制与初始实验预算

2026-09-18 核对官方资料：Python 支持流式响应，普通 Python Function 未压缩包上限为 500 MB；Fluid Compute 下 Hobby 最大时长为 300 秒。执行前仍需读取实际项目/runtime/套餐设置，不能假定旧项目已经启用相同上限。超大函数或延长时限的付费/Beta 能力不作为本验证前提。

初始实验参数均为部署配置，不写死到公共分析引擎：

- 若实际可用时长为 300 秒，业务预算先设 240 秒，额外预留 30 秒保存结果；若平台上限更低，自动降低实验预算或判定阻断，不能突破硬限制。
- 普通行情/搜索调用连接超时 5 秒、读取超时 20 秒；模型调用初始上限 90 秒，全部受剩余总预算约束。可恢复网络失败最多重试 1 次；不叠加 SDK 重试和上层重试，不自动重复整次分析。
- 问股初始最多 3 个推理/工具轮次、合计 5 次工具调用，输出 token 上限作为模型配置限制。工具仅允许本轮所需的行情/新闻/分析工具，禁止任意文件、本机 CLI 或用户指定服务端地址。
- 单账号最多一个在途计算请求，数据库原子限流；测试批次数有限。固定模型/数据源由环境配置选择，不在代码写死账号或供应商。
- 体积目标低于 400 MB，峰值内存目标低于实际上限的 80%，作为留有余量的验收目标；超过目标但未越平台硬上限也必须记录风险，不自动升级套餐。
- SSE 心跳只解决连接空闲，不延长函数时限。客户端停止读取不等于计算已取消；不承诺服务器强制终止不可中断的第三方调用。

## 5. 持久化与权限设计

浏览器继续使用现有 Supabase SDK/RLS 读取个人数据。计算端验证真实 Supabase 身份、app_members 状态和执行 owner，再进行受信任写入；单用户不等于匿名公开计算端点。

持久数据分为：自选股与非敏感用户偏好、执行状态/输入快照、报告及附件、问股会话/消息。模型密钥等部署配置保存在 Vercel 环境变量，不放入 Supabase 用户可读记录或前端产物。

先追踪三条链路实际调用的存储方法及写入位置，形成完整矩阵。优先以既有 SQLAlchemy 模型和 repository 接入 Supabase Postgres 的非公开引擎 schema，采用适配函数计算的受限连接数/pooler；仅迁移这些链路必需的表和依赖表。不能直接在远端运行全量 create_all，也不能声称换个 DSN 就完成兼容。SQLite 特有 SQL、upsert、自增与 JSON/时间字段必须有真实 PostgreSQL 测试。

与前端共享的结果继续复用已有发布器及 public 报告表；会话和执行状态由显式 repository/API 访问，public 新表必须包含 owner 并配置最小 grants/RLS。不在整个项目引入长期 SQLite↔Postgres 双主同步，不重构无关业务模块。

临时文件仅用于请求内可再生成缓存/中间产物，放独立临时目录；不能把配置、会话或最终报告留在 /tmp 当持久数据。报告上传成功且数据库提交后才能返回业务成功；SSE 最终完成事件必须反映保存是否成功。无法保存时返回明确结果，不回退到本机数据库。

新执行表拟为 `execution_runs`，包含 owner、kind、幂等键、状态、deadline、结果引用、运行标识和脱敏错误。唯一约束防止重复启动；终态不可被迟到回写覆盖。硬终止留下的运行状态通过下次查询/管理员核对识别为过期待核对，不依赖 finally 保证修复，也不自动重跑可能已收费的模型。旧 `analysis_tasks` 发布状态保持原语义。

## 7. 观测与证据格式

每次远端样本记录：部署 ID、提交/源码指纹、依赖锁定摘要、Python 版本、区域、runtime 设置、随机进程启动 ID、是否该进程首次请求、请求类型、总耗时、业务阶段耗时、首个 SSE 事件/答案事件耗时、成功数据源/失败原因、降级/缓存标记、模型调用数与可获得 token 用量、Supabase 提交结果。

冷启动分别报告平台可见初始化数据、模块 import 到 ready、客户端端到端首调用时间。新部署第一请求只是冷启动候选，需进程启动标识证据，不能将重新加载网页当成冷启动。

内存使用 RSS 采样、进程/子进程统计并尽量交叉核对平台指标；流式问股和同步分析都测。Python tracemalloc 不能代表 numpy/pandas 原生内存；warm 实例的 ru_maxrss 是进程历史高水位，不能当单请求峰值。若平台未暴露容器峰值，明确记录“采样观测峰值，非完整容器峰值”，不能填猜测值。

证据表字段：功能、样本数、构建体积、冷/热耗时列表、观察峰值、数据源成功/尝试次数、结果落库与附件校验、跨部署读取、失败原因、结论。报告内容/Token 不进入公开日志，截图和原始证据保存在仓库外。

## 8. 继续或停止的规则

- 三条链路逐项判定：通过 / 有条件通过 / 未通过。只有通过项进入正式站点；部分成功不等于整体通过。
- 打包或初始化不能通过：保留失败证据，停止功能迁移；不自动换付费资源。
- 单次执行超预算或内存不达标：缩小数据窗口/工具范围后重测，仍失败则明确功能暂不可用；不将工作丢给无人维护的后台线程。
- 持久化或权限不通过：不开放计算入口，即使分析输出正确。
- 全部关键关卡通过后才讨论分步综合分析：先复盘，再逐只分析，最后基于已保存结果汇总，每步可查看和显式重试；浏览器关闭不承诺剩余步骤自动完成。
- 小规模回测另设股票数、日期跨度、数据量上限，按同一真实远端验收矩阵验证后开放。重型选股、全量批处理不随之自动解锁。
