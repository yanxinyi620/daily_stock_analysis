# 模型回退链路可观测性修复设计

## 背景

个股分析配置 `codex_cli` 为主生成后端、LiteLLM 为备用后端时，主后端失败会自动回退到 DeepSeek。当前实现只返回最终结果，没有保留主后端错误；同时审计上下文沿用最初的 `codex_cli` transport，成功日志也使用配置模型而非实际成功模型。因此用量、日志和运行流程对同一次调用给出了互相矛盾的信息。

## 目标

- 保留并展示每次生成尝试的脱敏结果，包括主后端失败和备用模型链路。
- 成功日志、历史报告和用量记录均使用实际成功模型。
- 用量记录的 transport 反映实际执行通道；DeepSeek API 回退记为 `litellm`。
- 不记录完整 Prompt、API Key、认证信息或未经脱敏的 CLI 输出。
- 保持现有自动回退和报告生成行为不变。

## 设计

### 生成后端结果

扩展生成结果的诊断元数据，使后端切换时能够携带前序失败尝试。每次尝试至少记录：

- backend
- provider/model（可用时）
- stage
- error_code/reason
- success/failure
- fallback_model（进入备用模型时）

错误字段进入诊断前统一经过现有脱敏函数。

### LiteLLM 模型链

LiteLLM 主模型与备用模型的每次失败都加入同一诊断链，最终成功模型也写入链路。若所有模型均未通过 JSON 校验并采用最后一次文本兜底，诊断状态标记为 degraded，不伪装成完全成功。

### Analyzer 与用量

Analyzer 使用生成结果返回的实际模型和实际 transport：

- 成功日志输出实际成功模型。
- `model_used` 保持最终实际模型。
- `persist_llm_usage` 接收的 usage 中，transport 由实际执行后端设置，不从最初选择的 Codex 审计上下文继承。
- Codex CLI 本身没有可靠 token 数据时仍不创建虚构用量；其失败只进入运行诊断。

### 运行流程

运行诊断将模型尝试转换为顺序节点或重试/回退边，例如：

`Codex CLI 失败 → DeepSeek Flash 失败 → DeepSeek Pro 成功`

汇总中的模型使用最终成功模型；`failed_attempts` 和 `fallback_count` 根据真实尝试链计算。

### 兼容性

新增诊断字段采用可选结构。旧历史没有尝试链时继续使用现有单模型展示，不进行数据回填。API 不删除或重命名现有字段，Web 客户端可渐进消费新增数据。

## 错误处理与安全

- 只公开稳定错误码和脱敏摘要。
- CLI stdout/stderr 仅允许现有长度限制后的脱敏预览进入内部诊断，不进入普通用量接口。
- 回退诊断记录失败不得阻断分析主流程。
- 主后端和备用后端全部失败时，维持现有结构化错误行为。

## 测试

- Codex CLI 校验失败后回退 LiteLLM：断言保留 Codex 失败原因。
- Flash 失败、Pro 成功：断言尝试顺序、最终模型及 fallback 标记。
- 回退成功后的用量：断言 model 为 Pro、transport 为 `litellm`。
- 成功日志：断言使用实际模型，不再输出 Codex 成功。
- 运行流程：断言失败节点、回退边、最终成功节点及汇总计数。
- 脱敏测试：诊断中不出现密钥、认证头或完整敏感输出。

## 非目标

- 不改变模型优先级或回退策略。
- 不修改 Codex CLI、DeepSeek 的超时与重试次数。
- 不回填旧用量或旧历史的缺失诊断。
- 不新增模型费用估算。

## 回滚

移除新增尝试诊断字段及其消费逻辑即可恢复原行为；生成与回退主流程不需要迁移或数据回滚。
